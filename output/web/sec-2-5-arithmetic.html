    Section 2.5 Arithmetic

    In this section, we’ll take a closer look at expressions that calculate a value using arithmetic. As a quick refresher, an expression is a piece of program code that represents or computes a value. An expression can be a literal, a variable, a method call that evaluates to a value, or several of these things combined with operators such as + and >. The value of an expression can be assigned to a variable (as on lines 19, 22, 25, 28, 32, 33, and 34 of Listing 2.1), used as a parameter in a method call (lines 21, 24, 27, and 37), or combined with other values into a more complicated expression (lines 32, 33, 34, and 37). Expressions are an essential part of programming. In this section we will dig into the details of arithmetic expressions—expressions that evaluate to a numeric value. You will learn how to build them, what operations are available in Java, and how to avoid some of the common errors that arise because of the underlying fixed-space binary representation. Later we will cover expressions that evaluate to non-numeric results, such as the boolean and String values.
    🔗
    The basic building blocks of expressions are literals (such as 674, 3.14, true, 'X', and "Hello"), variables, and method calls that return a value. Arithmetic expressions are composed of numeric operands and operators. Operands are expressions that evaluate to a number (an integer or floating-point value). Consider Line 32 of Listing 2.1:
    🔗
    depthInFeet = depth / 12.0;
    The expression is on the right side of the assignment operator and is depth / 12.0. There are two operands—the expression depth and the expression 12.0. The first operand, depth, is a variable and evaluates to the value that is stored in the variable at the time that the statement executes. The second operand is a literal and evaluates to what is literally typed in the program—12.0. There is one operator—/—which is the division operator in Java.
    🔗

    Subsection 2.5.1 Arithmetic Operators

    Let’s begin with the basic arithmetic operators that are going to work as you expect: + (addition), - (subtraction) and * (multiplication). Each of these operators takes two operands: one on each side of the operator. The addition operator will add together the values of its two operands, so the result is the sum. The subtraction operator will subtract the value of the second operand from the first, so the result is the difference, and the multiplication operator will multiply together the values of the two operands, so the result is the product.
    🔗
    Let’s look at three straightforward examples that use all literal operands:
    🔗
    int total = 90 + 85;
double difference = 500.0 - 200.0;
int product = 3 * 5;
    After these three lines of code execute, total will have the value 175, difference will have the value 300.0, and product will have the value 15. Now let’s look at three more examples, just to illustrate that the operands in arithmetic expressions can be more complicated than a single literal.
    🔗
    total = stdin.nextInt() + stdin.nextInt();
difference = (first + second) / 2.0 - (third + fourth) / 2.0;
product = quantity * 5;
    In the more complicated expressions, you can see that the operands to arithmetic expressions can be method calls (stdin.nextInt()), other arithmetic expressions ((first + second) / 2.0 - (third + fourth) / 2.0), and they can include variables (first, second, third, fourth, and quantity). These can be combined, as long as each unit is an expression that evaluates to the correct type of number.
    🔗
    The only (slightly) tricky part for new programmers is learning that a multiplication will only take place if we use the asterisk * operator. You cannot append two variables, or a literal and a variable together, to perform multiplication (e.g. we might write \(5x\) in Algebra, but in Java if you have a variable x you cannot multiply it by five by writing 5x), similarly, we cannot append an expression with parentheses to perform multiplication, again, as we might in Algebra—\(5(x)\)—and there are no other multiplication operators, such as the dot or \(\times\text{.}\) If you want to multiply two numeric expressions together, you must put an asterisk between them.
    🔗
    Division in Java (and many other languages, including C, C++, and C#) might work a little differently than you expect. The arithmetic operators are overloaded. This means that they are defined for different data types. For now, we will consider just two broad categories—integers and reals. If we have two integer operands on either side of +, -, or *, then Java knows to perform an integer addition, subtraction, or multiplication. If we have two real operands, then Java knows to perform a floating-point addition, subtraction, or multiplication. Those operations are handled differently at the hardware level, but they always give us the answer we expect (unless something goes wrong), so we might not even question why they work for both types of numbers.
    🔗
    The division operator is also overloaded—it works for both integer and real operands—but integer division and floating-point division are two different operations. When we use a standard calculator to divide, if the result has a decimal part, we see it. For example, if we divide 10 by 4, we will get the result 2.5. In Java, if we divide integer 10 by integer 4, we get the result 2. An integer division shows us how many whole times the divisor fits into the dividend. There are two whole 4s in 10. Another way to think of it is that the decimal part is simply truncated off.
    🔗
    However, if either of the operands is a floating-point expression, then Java will perform a floating-point division. For example, 10.0 / 4, 10 / 4.0, and 10.0 / 4.0 will all evaluate to 2.5.
    🔗
    This is a very common source of errors for new programmers! One of the most common errors is calculating a percentage by dividing two integers and multiplying by 100. Consider the following code:
    🔗
    int score = 85; 
int total = 100; 
double percentage = score / total * 100.0; // Result is 0.0!
    New programmers naturally think that because percentage is declared as a double, a double division will be calculated. But both score and total are integers, so an integer division is calculated, resulting in zero. Even multiplying by the literal double 100.0 can’t save this calculation!
    🔗
    If you have two integers but you want to perform a floating-point calculation, you can cast one of them to a double, as follows:
    🔗
    double percentage = (double)score / total * 100.0;
    Because one operand is now a double, a floating-point division is calculated, and 85.0 is assigned to percentage. Note that this does not change the data type of the variable score—(double)score is simply an expression that evaluates to a double.
    🔗
    Now let’s look at an arithmetic operation that may not be familiar to you—modulus, or mod. Modulus is the companion to integer division. Where an integer division results in the number of whole divisors in the dividend, an integer modulus results in what is left over of the dividend, after the whole divisors have been removed. You may remember doing this sort of division before you learned how to calculate a division with a decimal result. You might have written, “13 divided by 3 is 4, remainder 1.” In Java, we write those two calculations as follows:
    🔗
    int quotient = 13 / 3;
int remainder = 13 % 3;
    Notice that in both calculations, we are writing the dividend, the operator, and the divisor. With the division operator, /, the result is how many whole times the divisor fits in the dividend. The value of quotient after this code executes is 4. With the mod operator, %, the result is the remainder (what’s left in 13) after you’ve taken as many whole divisors (3) out as you can. The value of remainder after this code executes is 1.
    🔗
    Although the concept is certainly familiar, the operation is probably new, so it is worth practicing with it to become accustomed to the order in which you write the operands and the result. This is a great use for JShell—practice with Java arithmetic and use JShell to check your calculations.
    🔗
    Modulus is surprisingly useful. If you calculate the mod of a sequence of numbers by the same divisor, for example the numbers 1%2, 2%2, …, 10%2, or 1%3, 2%3, … 10%3, you might notice that you get a result of zero when your divisor divides evenly into the dividend (e.g. 2%2, 4%2, 6%2, 8%2, and 10%2 are all zero, as are 3%3, 6%3, and 9%3). This can be used to determine if a number is odd or even (modding by two), or just evenly divisible by another number (if you want something to happen each time a count reaches the next multiple of 10, for example).
    🔗
    Note: If the first number is smaller than the second number, the result is simply the first number. For example, in 2 % 5, 5 fits into 2 zero whole times, leaving all 2 as the remainder.
    🔗
    It’s also useful when converting a total quantity into larger and smaller units, such as converting total seconds into hours, minutes, and seconds, for any operation that needs to “wrap around” (like a Caesar cipher), and for extracting digits from a number.
    🔗
    Now that we’ve covered the basic arithmetic operators, it’s worth talking about widening operations in some detail. We previously discussed narrowing in the context of assignment statements: if you assign a literal int to a variable of a smaller integer type (byte or short), Java will automatically narrow the int (convert it to the smaller type) if its value is within the range of values for that type.
    🔗
    Widening, you might have guessed, is the opposite operation—it is when Java automatically converts a value to a larger type. This can happen if you have two operands that evaluate to different types within the same expression. For example, let’s return to our percentage calculation from earlier:
    🔗
    double percentage = (double)score / total * 100.0;
    The calculation on the right contains a division between a double (score converted to double) and an integer (total). We already know Java performs double division, but how does it do that when one of the operands is an integer? Java will automatically widen the integer to the double type before performing the calculation. (Again, just as with the (double) casting, this doesn’t change the type of total. It is simply a behind-the-scenes operation that is performed so Java can calculate the division.)
    🔗
    Java will widen from a smaller data type to a larger. Java considers widening to be generally safe because the larger type has a much wider range (preventing overflow). Converting between integer types (int to long) or between floating-point types (float to double) never loses data. However, converting very large integers to float or double can occasionally lose some precision in the least significant digits because floating-point types store fewer significant bits. The widening order is:
    🔗
    int \(\to\) long \(\to\) float \(\to\) double
    🔗
    An expression of one type can be converted to another type only if it is to the right in the order. So an int can be converted to a long, float, or double, a long can be converted to a float or double, and a float can be converted to a double without any loss of information. If you have an expression that contains a float and a double, the float will be converted to double before the calculation is performed.
    🔗
    If you’re wondering why byte and short aren’t in the widening order, it’s because they (and variables of type char!) are always converted to the int type before a calculation.
    🔗
    Widening is also applied to assignment statements. For example, you might see an integer literal assigned to a double variable, as in:
    🔗
    double length = 20;
    The literal 20 will be widened to a double before being stored in the variable length. Remember the “bad” example of integer division from before? Here is the code, with a small change:
    🔗
    double percentage = score / total * 100; // Result is 0.0!
    The expression on the right, score / total * 100, is an integer division followed by an integer multiplication (integer calculations because both operands are integers for both operations). But the value stored in percentage is 0.0, because the entire expression on the right is evaluated first as an integer (producing 0), and only then is that final result widened to 0.0 as it is stored in the double variable.
    🔗
    🔗

    Subsection 2.5.2 String Conversion and Concatenation

    You may have noticed, in Listing 2.1, that the addition operator + is overloaded for another data type, String! On line 37, there is an expression that combines String literals with a double variable using the + operator.
    🔗
    System.out.println("You need " + cubicYards + " cubic yards of mulch.");
    When the addition operator is used with String operands, Java concatenates (appends) the two String operands together. If only one operand is a String, the other is converted to a String before the concatenation takes place. In the code above, the String “You need” is first concatenated with the value in the variable cubicYards. This is a double, so it is converted to a String version of the value in the double. (Suppose cubicYards holds 1.85, then the converted value is “1.85”.) The converted value is then concatenated with “You need”. The resulting String, “You need 1.85”, is then the first operand to a concatenation with the second string, “cubic yards of mulch.” Those two strings are concatenated together, resulting in “You need 1.85 cubic yards of mulch.”
    🔗
    🔗

    Subsection 2.5.3 Compound Assignments, Increment, and Decrement

    It is very common to perform a calculation on a variable and store the result back in the same variable. For example, in game software you might want to change the player’s score or health. The way an assignment statement is structured, there is an expression to the right of the assignment operator that is evaluated, and the result is then stored in the variable on the left. If you want to add to a variable, it must appear on both the right (in the calculation) and the left (as the variable being assigned into) of the assignment. For example, here we add one to a variable score that starts with a value of zero:
    🔗
    int score = 0;
score = score + 1;
    Here we subtract two from a variable health that starts with a value of five:
    🔗
    int health = 5;
health = health - 2;
    Java provides compound assignment operators (sometimes called augmented assignment operators in other languages) that combine the “variable = variable +” or “variable = variable -” part of the assignment into simply “variable +=” and “variable -=”. For example, here are our two assignments from above written with the compound assignment operators:
    🔗
    score += 1;
health -= 2;
    There are compound assignment operators for all of the arithmetic operators we just covered. Assume two variables x and y, which have already been given values:
    🔗
    x -= y; // same as: x = x - y;
x *= y; // same as: x = x * y;
x /= y; // same as: x = x / y;
x %= y; // same as: x = x % y;
    The combined assignment operator += even works with strings. Just as with numbers, text += " more"; is simply shorthand for text = text + " more";. It combines the value referenced by text with the string “more” and assigns the new result back to the variable text.
    🔗
    There is even a further shorthand for adding one to a numeric variable—the increment operator—and subtracting one from a numeric variable—the decrement operator. These two operators are widely used in Java. The increment ++ and decrement -- operators are unary operators, meaning they work on a single operand. They can be placed before (prefix) or after (postfix) the operand, but they work differently in the two positions.
    🔗
    When you apply the increment operator to a numeric variable, one is added to the variable’s value. When you apply the decrement operator, one is subtracted from the variable’s value. If the increment or decrement operation stands alone on one line, then it doesn’t matter if it’s prefix or postfix.
    🔗
    However, when we embed the increment or decrement operation in a larger expression, they behave differently. They both still increment or decrement the variable, but they do it at different times. If you use the prefix increment operator, the variable is incremented and then it is evaluated. If you use the postfix increment operator, the variable is evaluated and then it is incremented. It is the same for decrement.
    🔗
    Here is an example:
    🔗
    int score = 0;             // score is 0
score++;            // score is 1
score--;            // score is 0 
int x = ++score;    // x is 1, score is 1
int y = score++;    // y is 1, score is 2
    In our example, we have written int x = ++score;. Here we are using the prefix increment operator, so the value in score is incremented from 0 to 1 and then the expression is evaluated. It evaluates to 1, and that value is stored in the variable x. On the next line, we have int y = score++;. Here we are using the postfix increment operator, so score is evaluated. It evaluates to 1, and that value is stored in the variable y. It is then incremented to 2. So after the line executes, y holds 1 and score holds 2.
    🔗
    The confusion about when an incremented variable is evaluated is actually the source of many errors! This is another opportunity to try some increments, make predictions about the results, and use JShell to confirm them. Because mixing increment operators into larger mathematical calculations can lead to confusing and error-prone code, many professional software developers usually keep ++ and -- on their own separate lines (e.g., score++;). Keeping the increment on its own line achieves the exact same result while keeping your code less error-prone and easier to read.
    🔗
    🔗

    Subsection 2.5.4 The Math Class

    While basic operators handle everyday calculations like addition and multiplication, many programs require more advanced operations like finding a square root, raising a number to a power, or working with trigonometry. Like most programming languages, Java provides a built-in library of standard mathematical functions and constants, bundled together in the Math class.
    🔗
    Java’s Math class lives inside the java.lang package. You can reference classes inside this package by their name without an import statement.
    🔗
    A library cannot add symbols to Java, like \(\pi\) or \(\sqrt{\phantom{x}}\text{.}\) It can only build functionality using the language, so the math constants and functions are either variable names or methods that you will invoke. To use them, you will prepend them with the library name, Math. Here are tables of constants and some common methods:
    🔗
    You will note from Table 2.6 that the Math class offers the constants Math.PI, Math.E, and Math.TAU, which are useful in geometric, trigonometric, and scientific calculations. For example, you can use either Math.PI or Math.TAU when calculating the circumference of a circle.
    🔗
    The operations in Table 2.7 are among the most commonly used in programming. Some will be familiar from mathematics, such as sqrt(), round(), and pow() (although not necessarily by those names), while others may be new to you. You should practice with these in JShell to get comfortable passing the correct number and type of arguments, and to confirm how they work by comparing your predictions against JShell’s output. Begin with the examples in the table. The table might raise a few more questions than answers, so we’ll go over it here so you have the foundation needed to use these operations in a Java program.
    🔗
    The Math methods evaluate to (return) a value, which is why we refer to them informally as functions. Functions evaluate to a value. If a Math function returns a double, you can use that method call anywhere an expression of type double is valid, including on the right side of an assignment, as an operand in arithmetic, or as an argument to another method.
    🔗
    Notice that several operations accept double arguments. Java will automatically widen an int, long, or float argument to a double. So while Math.sqrt() expects a double argument, you can pass in an integer, and Java will convert it to a double before executing the method.
    🔗
    Let’s look at a few of these operations in more detail. Java doesn’t have an exponentiation operator, as some languages do. (The ^ symbol is the bitwise XOR operator, not the exponent operator.) Instead, you use Math.pow(base, exponent) to raise a number to a power. The first argument is the base, and the second is the exponent. While you will typically pass variables as arguments, literals illustrate how the argument order matters: Math.pow(5, 2) evaluates to \(5^2\text{,}\) or 25.0, whereas Math.pow(2, 5) evaluates to \(2^5\text{,}\) or 32.0. Note that Math.pow() always returns a double, even when the result is a whole number.
    🔗
    The Math.max() and Math.min() methods take two arguments and return the larger or smaller value, respectively. They are overloaded for int, long, float, and double, returning the same type as the arguments passed in. If you pass two different types (such as an int and a double), Java widens the narrower type and returns the wider type (in this example, double). If you need to find the maximum of three (or more) values, you can nest the calls: Math.max(a, Math.max(b, c)).
    🔗
    The Math.round(), Math.ceil(), and Math.floor() methods all handle rounding, but in different ways. Math.round() works as you expect from mathematics, with the floating-point argument being rounded to the closest whole number (and rounding up at .5). Math.ceil() always rounds up, and Math.floor() always rounds down. The return types of these methods are worth paying attention to! Math.round() returns an integer type, but which one depends on what you pass in. If the argument is a double, Math.round() returns a long, and if it’s a float, Math.round() returns an int. Both Math.ceil() and Math.floor(), however, return a double, not an integer type.
    🔗
    The Math.random() method generates a pseudo-random double value in the range of 0 (inclusive) to 1 (exclusive), meaning the value generated can be 0.0, but it will always be less than 1.0. To scale this value to an integer range, multiply by the number of possible outcomes (max-min + 1), convert to an int, and then add the minimum value. The following two examples will help illustrate this process. The first generates a pseudo-random value between 18 and 110, and the second between 1 and 6. Note that it’s very important to place parentheses around the multiplication before casting. If you cast the result of Math.random() to an integer, it will always be 0!
    🔗
    int age = (int)(Math.random() * 93) + 18; // Generates 18-110
int dieRoll = (int)(Math.random() * 6) + 1; // Generates 1, 2, 3, 4, 5, or 6

Some of the operations might not work as you expect. First, the trigonometric functions expect an input in radians, not degrees. The Math class provides a toRadians method that will convert degrees to radians, so if you have a value in degrees, you can convert it before passing it to a trigonometric function. Second, the log function is an \(\ln\) function—it is returning a natural logarithm. There is also a log10 function which returns the logarithm base 10.
    🔗

    🔗
    Let’s talk about how the Math class methods are used in Listing 2.9. On line 18, we invoke the Math.toRadians method and pass in the variable launchAngle as an argument. It is very common to put a value-returning method call to the right of the assignment and store the result in a variable for later use.

On line 21, Java will evaluate angleInRadians by looking up its value, pass that to Math.cos, and then multiply the return value by launchSpeed. The result of Math.round is then divided by 100.0, and the result of that expression is concatenated with the string “Horizontal Velocity :”. The String is then passed to the System.out.print method. Math.round must return a result that can then be divided by 100.0.     Subsection 2.5.5 Precedence Rules

    One thing we’ve glossed over in our discussion of arithmetic is order of operations—the rules that Java uses to resolve evaluation order within an expression that contains multiple operations. You probably learned the memory aid PEMDAS in school to help you evaluate a mathematical expression containing more than one operator. (If you didn’t, PEMDAS stands for Parentheses, Exponentiation, Multiplication and Division, Addition and Subtraction.) Java preserves the PEMDAS order of operations. However, programming languages have many more operators than the ones in PEMDAS, so as we learn operators, we must learn how they fit into the order of evaluation.
    🔗
    Here is a precedence table for the operators we’ve learned so far:
    🔗
    One term in this table that we also haven’t discussed is associativity, which you can see is either left-to-right or right-to-left. When an expression contains operators of different precedence levels, Java uses precedence to determine which operation to perform first (such as performing multiplication before addition). But what happens when an expression contains two or more operators with the same precedence?
    🔗
    In that situation, Java relies on associativity as a tiebreaker.
    🔗
    • Left-to-right associativity.
      Operations are grouped from left to right. All standard arithmetic operators (*, /, %, +, -) are left-associative. For example, 12 - 4 - 2 is grouped as (12 - 4) - 2 (evaluating to 6), rather than 12 - (4 - 2) (which would evaluate to 10).
      🔗
      🔗
    • Right-to-left associativity.
      Operations are grouped from right to left. The most common example is the assignment operator (=). In the expression x = y = 5;, Java groups the expression as x = (y = 5);, assigning 5 to y first, and then assigning that result to x.
      🔗
      🔗
    You can think of both precedence and associativity as determining where Java places invisible parentheses: Java groups by precedence first, and then for operators with the same precedence, Java groups by associativity.
    🔗
    You may not have thought of unary plus and minus as operators. You see unary minus when you write a negative literal (such as -5), and we think of the minus sign as part of the number. It is an operator, though, and it has a higher precedence than the arithmetic operators, as you can see.
    🔗
    A common misconception among students who have learned PEMDAS is that multiplication has a higher precedence than division, and that addition has a higher precedence than subtraction, because of their order in the mnemonic. However, multiplication, division, and mod all have the same level of precedence. If they appear in the same expression, the associativity (left-to-right) is used to determine the order in which they are calculated. It is the same with addition and subtraction. (This is no different from how these operations work in math.)
    🔗
    When you are writing code, it is a good idea to make the order of calculations explicit with parentheses. Other programmers may not, however, so it is important that you understand the order in which operations will be evaluated in an expression so that you can read others’ code. (And look it up if you don’t remember!)
    🔗

    Subsection 2.5.6 Pitfalls of Finite Binary Representation

    When we do math on paper, numbers have infinite precision, and we can write numbers as large as our paper allows and use symbols to represent infinite repetition. Computers, however, do not have infinite space. In Java, every numeric type is stored in a finite number of bits using binary (base 2).
    🔗
    Because memory is finite and many common decimals cannot be represented exactly in binary, programs sometimes produce surprising mathematical results. Understanding these limitations early will save you from subtle bugs down the road.
    🔗

    Subsubsection 2.5.6.1 Integer Overflow and the “Odometer” Effect

    In Java, an int is stored in 32 bits, meaning it can only represent integers from \(-2{,}147{,}483{,}648\) to \(+2{,}147{,}483{,}647\text{.}\) Java provides handy constants in the standard library to represent these boundary values: Integer.MIN_VALUE and Integer.MAX_VALUE.
    🔗
    What happens if you have the largest possible integer and try to add 1 to it, as in the code below?
    🔗
    int max = Integer.MAX_VALUE;
System.out.println("Maximum int: " + max);
System.out.println("Max plus one: " + (max + 1));
    This code will print:
    🔗
    Maximum int: 2147483647
Max plus one: -2147483648
    Adding 1 to the maximum positive integer does not produce an error, nor does it stop at the maximum. Instead, it silently overflows and wraps around to the lowest possible negative number (Integer.MIN_VALUE).
    🔗
    Think of this like an old mechanical car odometer that reaches 999999 and rolls over to 000000. In Java’s two’s-complement binary system, rolling over the highest positive number lands squarely on the smallest negative number.
    🔗
    Similarly, underflow occurs if you subtract 1 from Integer.MIN_VALUE—it wraps around to Integer.MAX_VALUE.
    🔗
    Note that Java does not warn you when an integer overflows. If your program might handle quantities larger than 2 billion (such as bank balances, file sizes in bytes, or national populations), use the 64-bit long type instead of int. Be especially careful about variables storing temporary results of additions or multiplications. Your data may always fall within the integer range, but if a calculation with your data might result in a value outside the range, use a long.
    🔗
    🔗

    Subsubsection 2.5.6.2 Inexact Decimals in Base 2

    We are accustomed to the base-10 decimal system. In decimal, simple fractions based on prime factors of 10 (2 and 5) do not repeat. For example, \(1 / 2 = 0.5\text{,}\) \(1 / 2^2 = 1 / 4 = 0.25\text{,}\) \(1 / 5 = 0.2\text{,}\) and \(1 / (2 \times 5) = 0.1\text{.}\) However, fractions with other denominators repeat, for example, \(1 / 3 = 0.3333333\ldots\text{.}\)
    🔗
    Computers do not use base 10; they use base 2 (binary). In binary, the only prime factor is 2. As a result, only fractions whose denominators are powers of two (e.g. \(1 / 2\text{,}\) \(1 / 4\text{,}\) \(1 / 8\text{,}\) \(1 / 16\text{,}\) etc.) terminate.
    🔗
    You might have noticed that 10 is not a power of 2! So a fraction such as \(1 / 10\) cannot be represented (as a decimal) in a finite number of binary bits. In base 2, 0.1 becomes an infinitely repeating binary fraction:
    🔗
    \begin{equation*} 0.1_{10} = 0.0001100110011\ldots_2 = 0.0\overline{0011}_2 \end{equation*}
    Because a double has only 53 bits of precision to store the fractional part, it must round off this infinite repetition. Try this in JShell:
    🔗
    jshell> 0.1 + 0.2
$1 ==> 0.30000000000000004
    Because of this tiny rounding discrepancy, adding 0.1 ten times in a program will yield 0.9999999999999999, not 1.0.
    🔗
    Don’t worry—programmers deal with this every day, and there are standard strategies for working around it. Because floating-point numbers are almost always close approximations rather than exact values, we will see in Chapter 3 that you should avoid checking whether two numbers are strictly equal. Instead, you check whether the difference between them falls within an acceptable threshold.
    🔗
    And if you ever need exact decimal arithmetic for monetary calculations, Java provides a dedicated class called BigDecimal.
    🔗
    🔗

    Subsubsection 2.5.6.3 Finite Precision and “Lost” Operands (Absorption)

    A double can represent astonishingly large numbers (up to approximately \(1.8 \times 10^{308}\)) by using scientific notation under the hood: a significand (the digits) multiplied by an exponent (\(2^{\text{power}}\)). However, a double only has enough space to preserve approximately 15 to 17 decimal digits of precision.
    🔗
    Before a computer can add two numbers in scientific notation, it must normalize them so that their exponents match. When you add a tiny number to a massive number, the computer shifts the decimal point of the smaller number so far to the right that its significant digits fall off the edge of available memory:
    🔗
    double massive = 10_000_000_000_000_000.0; // 10^16 (16 digits)
double small   = 1.0;
double sum = massive + small;
System.out.println("Massive number: " + massive);
System.out.println("Sum with 1.0  : " + sum);
System.out.println("sum - massive: " + (sum - massive));
    This produces the following output:
    🔗
    Massive number: 1.0E16
Sum with 1.0  : 1.0E16
sum - massive: 0.0
    The 1.0 was completely “absorbed” (lost) because \(10^{16}\) already consumes all 16 digits of precision that a double can track. To the computer, \(10^{16} + 1.0\) is simply \(10^{16}\text{.}\)
    🔗
    🔗

    Subsubsection 2.5.6.4 Division by Zero: Integers vs. Floating-Point

    In mathematics, division by zero is undefined. In Java, how the system handles division by zero depends entirely on whether you are using integers or floating-point numbers.
    🔗
    If you attempt to divide an integer by zero, Java immediately halts execution and throws an error:
    🔗
    int result = 5 / 0; // Throws ArithmeticException: / by zero
    Unlike an integer zero (which represents an exact count of nothing), a floating-point 0.0 represents a point on a continuous number line. Following the IEEE 754 standard, Java treats dividing a real number by zero not as a fatal program crash, but as approaching mathematical infinity:
    🔗
    System.out.println(5.0 / 0.0);   // Prints: Infinity
System.out.println(-5.0 / 0.0);  // Prints: -Infinity
    If an operation is mathematically undefined and has no sensible representation on a number line, Java produces the special floating-point value NaN:
    🔗
    System.out.println(0.0 / 0.0);           // Prints: NaN
System.out.println(Math.sqrt(-4.0));     // Prints: NaN
    You can access these values directly through constants such as Double.POSITIVE_INFINITY and Double.NaN. If you ever see NaN or Infinity printed in your program’s output, check your computations—you likely divided by a variable that evaluated to zero or took the square root of a negative number.
