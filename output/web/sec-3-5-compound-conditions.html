    Section 3.5 Compound Conditions: Logical Operators & De Morgan’s Laws

    Sometimes we would like to test multiple conditions at once. For example, our precondition from Listing 2.22 is that both x >= radius and y >= radius. So far we haven’t seen a way to test two conditions in the same expression. Fortunately, Java (like most programming languages) has operators that allow us to logically combine Boolean expressions in two different ways: && (logical and) and || (logical or) to build compound logical expressions.
    🔗

    Subsection 3.5.1 Logical and && and or ||

    Let’s look at how to enforce the precondition from Listing 2.22. If we’ve obtained values for centerX, centerY, and radius, we can test that both centerX >= radius and centerY >= radius by combining the relational expressions with the && (logical and) operator:
    🔗
    centerX >= radius && centerY >= radius
    A logical and expression consists of two boolean expressions joined by the && operator. Each operand must be a complete boolean expression that evaluates to true or false. The two ampersand symbols that make up the operator must be written with no space between them. (Note that there is also a bitwise and operator which is a single ampersand &. This is a different operator! Be very careful to use && for logical and—Java will not flag bitwise and as a syntax error, and you could end up with a very difficult-to-find bug.)
    🔗
    When Java evaluates the expression, the boolean expressions on the left and right of the && operator are evaluated (theoretically; in practice it’s a little more complicated, as you’ll see in Subsection 3.5.5), and the entire expression will evaluate to true or false according to Table 3.12 (called a truth table).
    🔗
    In our code, centerX >= radius is Operand1 and centerY >= radius is Operand2. The truth table shows columns for the two operands to the && operation with all possible values for each operand. (Because each can only evaluate to true or false, there are only four possible combinations.) The third column shows the value of the entire && expression for each combination of operands.
    🔗
    A logical and expression works very much the way we use the word “and” in natural language—if both conditions are true, the whole expression is true. If either or both of the conditions are false, then the whole expression is false. Use && when you want the condition to be true only if both operands are true.
    🔗
    We can incorporate our expression into Listing 2.22 to test our precondition. If it is true, we proceed with calculations and output. If it is false, we avoid calculating coordinates that take the drone out of its allowed area. The code might look like this:
    🔗
    if (centerX >= radius && centerY >= radius) {
    perimeter = Math.PI * 2 * radius;
    // (the rest of the calculations)
    System.out.printf("%-14s %11s", "Waypoint", "Angle (deg)");
    // (the rest of the print statements)
}
    All of the calculation and printing code from Listing 2.22 is controlled by the if statement. We calculate and display the results only if the inputs meet the preconditions.
    🔗
    We can put a logical and expression anywhere we can put a boolean expression, including as the condition following if, on the right of an assignment to a boolean variable, or as an argument to a method call that expects a boolean parameter.
    🔗
    A logical or expression has the same construction as logical and, except we use the || (or) operator. Again, it is two pipe symbols written together with no space between, and like bitwise and, there is a single pipe operator which is bitwise or, which is a different operation. Each operand to a logical or operator must be a boolean expression. Table 3.13 is a truth table for logical or:
    🔗
    Note that || (or) evaluates to true if either or both of its operands are true. An || is false only when both operands are false.
    🔗
    In our soil-testing program, suppose we want to set a flag if the pH is off—either too high or too low. We can do this with a logical or:
    🔗
    boolean phProblem = (phLevel > 7.5) || (phLevel < 6.0);
    The flag phProblem will be set if either of the conditions evaluates to true—either pH greater than 7.5 or pH less than 6.0. (Note that in this case, it’s impossible for both conditions to evaluate to true at the same time—they are mutually exclusive. However, if we were testing two different variables, it could be possible for both to be true as well, in which case the entire expression evaluates to true.)
    🔗
    One caution with writing logical expressions: it’s tempting to write expressions that mirror our natural language, such as phLevel > 7.5 || < 6.0. In natural language, we might say “pH is greater than 7.5 or less than 6.0,” but we cannot translate that directly to a Java expression. Java will flag this as a syntax error (although there are other languages that will allow it, even though its meaning is not what we intend). We must have a complete Boolean expression on each side of the logical or operator. What we mean is that pH is greater than 7.5 or pH is less than 6.0, which we can translate directly to Java.
    🔗
    🔗

    Subsection 3.5.2 Testing Ranges

    Our code that sets the pH flag is an example of an out-of-range test: testing that a value falls outside of an expected range. A number line illustrates this clearly:
    🔗
    We use logical or to test whether a value falls outside of a range, because either the value is too low or it’s too high—it can’t simultaneously be both. We want to flag or act on the out-of-range value whether it is too low or it is too high.
    🔗
    We use logical and to test for a value in a range. Imagine the opposite test—a test for a soil pH that is within the expected range for our gardening scenario. On a number line, we would draw that as:
    🔗
    We write this expression as:
    🔗
    (phLevel >= 6.0) && (phLevel <= 7.5)
    We use logical and to test if a value falls within a range because our test must be true only if the value is both higher than the low end of the range and lower than the high end of the range.
    🔗
    In math (and some programming languages), you can write a within-range test without logical and, e.g. \(6.0 \le \text{phLevel} \le 7.5\text{.}\) Java will flag this as a syntax error, because the first expression (6.0 <= phLevel) will evaluate to true or false, making the rest of the expression either true <= 7.5 or false <= 7.5. In Java, the relational operators do not work on Boolean operands, so this is an error. You must use logical and to create a within-range test.
    🔗
    Note that we choose < or > if we are excluding an endpoint, and we choose <= and >= if we are including an endpoint. In this example, the endpoints are included in the expected range for healthy soil and excluded in the test for unhealthy soil. Whether endpoints are included or excluded from a test depends on the test and has nothing to do with whether we’re testing for a value inside or outside of a range.
    🔗
    🔗

    Subsection 3.5.3 Logical not (!)

    Java has one more logical operator: logical not (!). Logical not is a unary operator, meaning it has one operand: a boolean expression. Logical not negates the logical expression, as shown in Table 3.16:
    🔗
    Logical not operates on the expression immediately after it. For example, if we have a boolean flag lowPh and we want to print a message to the user if their soil does not have low pH, we might write the following code:
    🔗
    if (!lowPh) {
    System.out.println("Your soil’s pH is not too low. ");
}
    In Java, you can negate any Boolean expression but take care not to write expressions that are overly confusing. For example, can you easily tell when the following expression will evaluate to true?
    🔗
    !((phLevel >= 6.0) && (phLevel <= 7.5))
    Is it the same as this one?
    🔗
    !(phLevel >= 6.0) && (phLevel <= 7.5)
    The answer is no—they mean completely different things. In the first expression, the ! applies to the entire compound condition inside the outer parentheses. In the second, the ! applies only to the first comparison.
    🔗
    Why does ! bind so tightly to the first comparison instead of waiting for the &&? The reason comes down to operator precedence, which we will examine in the next section. In Subsection 3.5.6, you’ll learn how to simplify expressions like these. Simpler logic is easier to read and less prone to error.
    🔗
    A good rule of thumb for the logical not operator is to use it primarily to negate a single boolean variable, and to write a direct, simplified relational expression whenever you are comparing values (e.g., prefer x != y over !(x == y), and x >= y over !(x < y)).
    🔗
    🔗

    Subsection 3.5.4 Logical Operator Precedence

    Table 3.17 is our operator precedence table with &&, ||, and ! added. The new and changed rows are highlighted in bold.
    🔗
    Notice, first, that the logical not operator sits very high in the precedence table, alongside prefix and unary operators. Remember that precedence and associativity govern where Java places invisible parentheses before evaluation begins. Logical not will always be grouped with its operand before relational or binary logical operators take effect.
    🔗
    In our expression from the previous section:
    🔗
    !(phLevel >= 6.0) && (phLevel <= 7.5)
    Because ! has higher precedence than &&, the ! binds tightly to (phLevel >= 6.0). It negates that comparison first, and only then does Java evaluate the && between the two sides.
    🔗
    Notice also that && has higher precedence than ||. This means that when both appear in an expression without explicit parentheses:
    🔗
    boolean badPh = phLevel < 6.0 || phLevel > 7.5 && phLevel != -1;
    Java groups the && first, placing invisible parentheses like this:
    🔗
    phLevel < 6.0 || (phLevel > 7.5 && phLevel != -1)
    Imagine that a pH reading of -1 indicates a sensor error. We want badPh to be true only if we have a valid test that measured an unhealthy pH—never if the test itself was invalid.
    🔗
    Because of Java’s grouping, watch what happens when we substitute -1:
    🔗
    phLevel < 6.0 || (phLevel > 7.5 && phLevel != -1)
-1 < 6.0 || (-1 > 7.5 && -1 != -1)
true || (false && false)
true || false
true
    The programmer intended for the expression to evaluate to false when phLevel is -1, but because of operator precedence, the condition -1 < 6.0 sits on its own and the check for -1 is grouped with a high pH. The -1 < 6.0 condition evaluates to true, making the entire expression true.
    🔗
    Even worse, this expression compiles without error and behaves correctly for three out of four input categories (normal pH, high pH, and typical low pH). The bug remains completely silent until that -1 edge case occurs!
    🔗
    To ensure the || is evaluated as a combined unit, we must override the default precedence by adding explicit parentheses:
    🔗
    (phLevel < 6.0 || phLevel > 7.5) && phLevel != -1
    Enclosing expressions in parentheses is always best practice. It eliminates ambiguity, guarantees that Java groups your logic as intended, and ensures that anyone reading your code understands your purpose without having to consult a precedence table. Enclosing expressions in parentheses is always a good idea to make code more readable, even if you’re only clarifying the grouping order that already exists.
    🔗
    🔗

    Subsection 3.5.5 Short-Circuit Evaluation

    When Java evaluates a compound Boolean expression joined by && or ||, it does not always evaluate both operands. Instead, it stops evaluating as soon as the final truth value of the entire expression is guaranteed. This behavior is called short-circuit evaluation.
    🔗
    To understand why this is possible, look again at the truth tables for && and || (Table 3.12 and Table 3.13) and ask, before you read on, when can you predict the outcome of the expression by looking at the first operand?
    🔗
    • For &&: If the left operand evaluates to false, the entire expression must be false, regardless of what the right operand produces (false && anything is always false). Java stops immediately and skips evaluating the right operand.
      🔗
      🔗
    • For ||: If the left operand evaluates to true, the entire expression must be true, regardless of what the right operand produces (true || anything is always true). Java stops immediately and skips evaluating the right operand.
      🔗
      🔗
    When the left operand cannot decide the outcome, Java evaluates the right operand:
    🔗
    // If count is 0, the left side (count > 0) is false.
// Java short-circuits: it never evaluates the right side!
// If count is not 0, the right side is evaluated.
if (count > 0 && total / count > 10) { ... }
    Short-circuiting saves a few fractions of a second in computation time, but it also gives programmers the ability to prevent run-time errors with properly written compound expressions.
    🔗
    In Subsection 3.2.1, we saw that calculating freethrow percentages when totalFreethrows is 0 crashes the program with an ArithmeticException (division by zero). With short-circuit evaluation, we can write a guard condition directly inside our Boolean expression:
    🔗
    if (totalFreethrows > 0 && (double)successfulFreethrows / totalFreethrows >= 0.70) {
    System.out.println("Qualifies as an accurate shooter!");
}
    Notice the order of the operations:
    🔗
    1. Java tests the guard on the left: totalFreethrows > 0.
      🔗
      🔗
    2. If totalFreethrows is 0, that test evaluates to false.
      🔗
      🔗
    3. Because the operator is &&, Java short-circuits. It never attempts the division on the right side!
      🔗
      🔗
    4. The program safely skips the entire if block without crashing.
      🔗
      🔗
    If you had placed the division on the left side, or if Java did not short-circuit, the program would crash whenever totalFreethrows was zero.
    🔗
    This is also why using & and | instead of && and || is so dangerous: the single ampersand and pipe operators do not short-circuit. If you wrote totalFreethrows > 0 & ..., Java would evaluate both sides every single time, crashing your program when the totalFreethrows variable contained 0.
    🔗
    🔗

    Subsection 3.5.6 Complementing Logical Conditions with De Morgan’s Laws

    Back in Subsection 3.5.3, we posed a puzzling question: can you easily tell when this negated compound expression will evaluate to true?
    🔗
    !((phLevel >= 6.0) && (phLevel <= 7.5))
    Reading negated code is mentally taxing. Trying to reason about “not both greater than or equal to 6.0 and less than or equal to 7.5” forces your brain to juggle double negatives.
    🔗
    Fortunately, a 19th-century mathematician named Augustus De Morgan formulated two logical equivalence rules—known as De Morgan’s Laws—that allow us to simplify negated compound expressions into readable, maintainable code.
    🔗
    De Morgan’s laws describe how to distribute a ! across a parenthesized && or || expression:
    🔗
    !(A && B) -> !A || !B
!(A || B) -> !A && !B
    Simply put, complement each operand and switch a logical and to a logical or, and vice-versa.
    🔗
    You can think of the negation of a logical and as the or of the negations. Saying “It is not true that both A and B occurred” means “Either A did not occur, or B did not occur, or they both did not occur.” Another way to phrase that is, “at least one of A and B did not occur.”
    🔗
    Think of the negation of a logical or as the and of the negations. Saying “It is not true that either A or B occurred” means “Neither A nor B occurred.”
    🔗
    Let’s apply De Morgan’s laws to simplify our awkward expression from earlier:
    🔗
    !((phLevel >= 6.0) && (phLevel <= 7.5))
    Because the original expression used &&, we flip && to || and negate both sides:
    🔗
    !(phLevel >= 6.0) || !(phLevel <= 7.5)
    Replace each negated relational operator with its complement (from Table 3.5) and remove the not operators:
    🔗
    phLevel < 6.0 || phLevel > 7.5
    Look at the result: it is the exact out-of-range expression we wrote in Subsection 3.5.2!
    🔗
    This makes intuitive sense:
    🔗
    • The original condition, (phLevel >= 6.0 && phLevel <= 7.5), defined soil that was inside the healthy range.
      🔗
      🔗
    • Its complement, phLevel < 6.0 || phLevel > 7.5, defines soil that is outside the healthy range.
      🔗
      🔗
    Whenever you find yourself writing an ! outside a parenthesized condition, use De Morgan’s laws to push the negation inside and simplify each comparison. Your code will be significantly easier to read, test, and maintain.
