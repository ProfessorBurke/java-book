    Section 4.10 Reading Text Files with Scanner

    When you save a photo, adjust user settings, or write a Java program, that data is stored in a file on persistent storage (such as a solid state drive or hard drive). While data stored in RAM disappears the moment a program terminates, files on disk remain preserved. Almost every practical application interacts with files: reading configuration data when launching and saving user progress when quitting.
    🔗
    Being able to read from and write to files is a fundamental software engineering skill. It also saves immense testing time: rather than manually typing twenty lines of test input into the console every time you run a loop, you can store your test data in a text file and let your program read it automatically in milliseconds.
    🔗
    Files generally fall into two broad formats: binary or text. While all files on disk are physically stored as binary bits, a text file consists of bytes that represent a sequence of human-readable characters, typically encoded using the universal UTF-8 standard. Fortunately, you don’t need to worry about manually translating raw bytes into characters—Java’s Scanner class handles all the decoding behind the scenes. In fact, once you open a file, reading from it uses the exact same Scanner methods you already know!
    🔗

    Subsection 4.10.1 The File Class

    When we created a Scanner to read user input from the keyboard, we passed System.in to the Scanner’s constructor with a line of code such as Scanner stdin = new Scanner(System.in). If we want to read from a file with a Scanner, we can use a different Scanner constructor that takes a File object as a parameter. To use that constructor and read from a file, we must first create the File object.
    🔗
    In Java, the File class (located in the java.io package) represents a file or directory pathway on your operating system. A File object does not actually open the file or read its data; think of it as a programmatic address label pointing to a location on your disk.
    🔗
    To create a File object, pass the file’s path as a string to the constructor. If you pass just the filename (such as "data.txt"), you are using a relative path. Java resolves relative paths against the program’s current working directory.
    🔗
    import java.io.File;
// ...
File dataFile = new File("data.txt");
    In Eclipse, the default working directory is the project root folder—the folder containing src and bin, not the src folder itself! When adding a text file to your project in Eclipse, drag or create it directly in the top-level project folder. If you place it inside src, Java will not be able to find it using just the file’s name.
    🔗
    The File class provides helpful utility methods to inspect a file before attempting to read it. For example, you can call exists() to verify that a file is present on disk:
    🔗
    if (dataFile.exists()) {
    System.out.println("File found! Ready to process.");
} else {
    System.out.println("Error: Could not locate " + dataFile.getAbsolutePath());
}
    The getAbsolutePath() method returns the full operating-system file path (e.g., C:\Users\...\project\data.txt), which is invaluable for debugging when your program cannot find a file.
    🔗
    🔗

    Subsection 4.10.2 Creating a File-Reading Scanner

    Once you have created a File object, you can create a Scanner to read from the file. The File object itself gives us some operating system access (such as determining if a file exists at the path we passed to the constructor). It does not give us methods for reading from the file.
    🔗
    Creating a Scanner that can read from a file is easy. This code will create a Scanner to read from the file "data.txt", assuming the code above that created the dataFile object:
    🔗
    Scanner fileScanner = new Scanner(dataFile);

    Subsubsection 4.10.2.1 Checked Versus Unchecked Exceptions

    There is one additional requirement when creating a Scanner that reads from a file: we must acknowledge the possibility that the file might not be there.
    🔗
    In Java, errors that occur while a program is running are represented by exceptions. You have already seen unchecked exceptions, such as the ArithmeticException that occurs if you divide an integer by zero:
    🔗
    Exception in thread "main" java.lang.ArithmeticException: / by zero
    And as you may have already experienced, when an exception is thrown, the program crashes with a red error message.
    🔗
    Java divides exceptions into two categories: checked exceptions and unchecked exceptions. It is a programmer’s responsibility to handle checked exceptions using special exception-handling code because they represent a catastrophic event that is outside of the programmer’s control. We must write defensive code so our program can recover gracefully.
    🔗
    Unchecked exceptions, like the ArithmeticException, are generally thrown when there’s a programming error (a bug). Those should be resolved by fixing the error in the code. We don’t have to write special exception-handling code to handle them—we just need to fix the bug so they don’t happen again.
    🔗
    But checked exceptions are different. These represent exceptional conditions that are outside of the programmer’s direct control, such as a network connection dropping or a file missing from the hard drive. Even if your code is 100% bug-free, a user might accidentally delete data.txt or misspell its name.
    🔗
    Because missing files are an ever-present reality of interacting with operating systems, FileNotFoundException is a checked exception. Java enforces a strict rule: you must acknowledge checked exceptions in your code, or the compiler will refuse to compile your program.
    🔗
    🔗

    Subsubsection 4.10.2.2 Throwing Checked Exceptions

    When code might trigger a checked exception, Java gives you two choices:
    🔗
    1. Handle it: Catch the exception using a try-catch block and recover gracefully (for example, by prompting the user for a different filename). We will learn how to write try-catch blocks in a future chapter.
      🔗
      🔗
    2. Declare it (“Pass the buck”): Acknowledge that the exception might happen and let it pass up to the caller. Because our focus right now is on learning loops and file processing, we will choose the second option: declaring that our main method might throw the exception.
      🔗
      🔗
    To do this, add a throws clause to the main method header:
    🔗
    import java.io.File; 
import java.io.FileNotFoundException; // Required import! 
import java.util.Scanner; 
 
public class FileReadDemo { 
    public static void main(String[] args) throws FileNotFoundException { 
        File dataFile = new File("data.txt"); 
        Scanner fileScanner = new Scanner(dataFile); // Now the compiler is happy! 
        // ... 
    } 
}
    You can also write throws IOException. IOException (Input/Output Exception) is the broader parent class that encompasses file errors, so either is acceptable.
    🔗
    When you omit the throws clause, Eclipse flags new Scanner(dataFile) with a red squiggly underline. Clicking the lightbulb in the margin reveals the Quick Fix: Add throws declaration, which will insert the clause and the import automatically.
    🔗
    (Note: If the file actually is missing when your program runs, passing the exception out of main means the JVM will halt your program and display the red stack trace in the console).
    🔗
    🔗

    Subsubsection 4.10.2.3 Who’s Throwing the Exceptions

    You might wonder why programming languages use the terms “throw” and “caught.” Think of an exception like a hot potato:
    🔗
    1. The exception originates inside a method when something fails: In our code, when new Scanner(dataFile) looks for "data.txt" and cannot find it on disk, the Scanner constructor halts its work and throws a FileNotFoundException object backward to the method that called it (main).
      🔗
      🔗
    2. The calling method must respond: When main receives that thrown exception, it must either catch it (handle it) or throw it again up to whatever called main.
      🔗
      🔗
    3. The Call Chain: Exceptions travel backward along the call chain—the sequence of method calls that led to the problem. If main() called a method named openFile(), and openFile() called the Scanner constructor:
      🔗
      main() ---> openFile() ---> Scanner constructor
      🔗
      If the file is missing, the Scanner constructor throws the exception to openFile(). If openFile() does not handle it, it throws it back to main(). Any method that does not handle the exception must have the throws clause in its header.
      🔗
      🔗

    Subsection 4.10.4 Reading from a File in a Loop Mixing Tokens and Lines

    We have now read one record of information from a file. In real-world data processing, however, a file almost always consists of an unknown number of records, each with the same format but different data. We will now expand our program to read zero, one, or hundreds of city records from a file, where each record consists of a city name, latitude, longitude, and AQI, in that order.
    🔗
    To read an arbitrary number of records from a file, we use a loop and either the hasNext() or hasNextLine() Scanner method. The hasNext() method looks ahead and returns true if there is another non-whitespace token (a word or number) left in the file, ignoring any spaces or blank lines.
    🔗
    In contrast, the hasNextLine() method returns true if the Scanner has not yet reached the end of the file—meaning there is another line of input available, even if that line is completely empty.
    🔗
    Within the loop, we read and process one complete city record. Listing 4.19 is an update to our last program that reads every record of AQI data from the file aqi_data.txt:
    🔗
    This program is very similar to Listing 4.18, with a few important changes. Once we have confirmed that the file exists and created the Scanner on line 23, we begin a file reading loop using fileScanner.hasNext() as the loop entry condition. If the file is empty, we will simply never enter the loop, the Scanner will be closed on line 42, and the program will terminate.
    🔗
    If the file isn’t empty, execution enters the loop and reads and processes one complete record of data.
    🔗
    As with Listing 4.18, this loop operates under the precondition that the file is well-formed. If the file is corrupted, for example, if a latitude coordinate is missing or contains letters like "NA", Java will halt with an InputMismatchException or NoSuchElementException. In a future chapter, you will learn how to write exception-handling code to recover from corrupted files gracefully.
    🔗
    A critically important (and potentially confusing) line in this loop is on lines 32-34:
    🔗
    if (fileScanner.hasNext()) {
    fileScanner.nextLine();
}
    These lines appear immediately after we have read a complete single record from the file. If we omit this check, our program will throw an InputMismatchException before it reads the second record. Here is the domino effect that occurs if line 33 is omitted:
    🔗
    1. On line 29, fileScanner.nextInt() reads the AQI integer (e.g., 42). As we learned in Chapter 2, token-reading methods leave the trailing newline character (\n) sitting in the input stream.
      🔗
      🔗
    2. Control circles back to the top of the loop, and line 26 executes: name = fileScanner.nextLine().
      🔗
      🔗
    3. Because a newline was left behind, nextLine() immediately swallows that empty newline, storing an empty string ("") into name.
      🔗
      🔗
    4. Next, line 27 attempts to read a double for latitude. But because the scanner is out of alignment, the next piece of text waiting in the file is the city name of the next city (such as "San Francisco").
      🔗
      🔗
    5. Java cannot convert "San Francisco" into a double, causing an immediate InputMismatchException.
      🔗
      🔗
    Lines 32–34 prevent this by consuming the leftover newline after the AQI is read, queuing up the scanner so it is poised at the start of the next city name when the loop repeats.
    🔗
    You might ask: Why not just write fileScanner.nextLine(); without the if check?
    🔗
    Because of what happens at the very end of the file. If the file has no trailing newline after the final AQI number, calling nextLine() at the bottom of the last record would attempt to read past the end of the file, crashing your program with a NoSuchElementException. By checking if (fileScanner.hasNext()) first, we only consume the newline if another real data record actually follows, ensuring the loop terminates cleanly on the final record.
    🔗
    🔗

    Subsection 4.10.5 Reading from a File in a Loop Reading Lines and Converting

    Another approach to reading records from a file is to separate reading from type conversion. In this approach, we read each line as raw text using nextLine() and then convert it using two utility methods: Integer.parseInt() and Double.parseDouble(). In fact, these are the exact methods that Scanner calls behind the scenes inside nextInt() and nextDouble() to convert text tokens into numeric values.
    🔗
    We can replace lines 26-34 in Listing 4.19 with the following reading and conversion lines:
    🔗
    name = fileScanner.nextLine();
line = fileScanner.nextLine();
latitude = Double.parseDouble(line);
line = fileScanner.nextLine();
longitude = Double.parseDouble(line);
line = fileScanner.nextLine();
aqi = Integer.parseInt(line);
    In this code, each numeric value is now read on one line and parsed on the next, e.g. we read the line containing the latitude value on line 27, and we convert it to a double on line 28.
    🔗
    The Double.parseDouble() method is a utility method that takes a String version of a real number as a parameter and returns a numeric double. Similarly, Integer.parseInt() takes a String version of an integer and returns a numeric int. These methods will throw a NumberFormatException if the argument is a String that cannot be converted to the numeric type.
    🔗
    Our approach uses a temporary String variable line to read a line from the file before converting, but it is common practice to combine each read/parse pair into a single line by passing the String result of nextLine() to the parsing methods parseInt() and parseDouble():
    🔗
    name = fileScanner.nextLine();
latitude = Double.parseDouble(fileScanner.nextLine());
longitude = Double.parseDouble(fileScanner.nextLine());
aqi = Integer.parseInt(fileScanner.nextLine());
    This doesn’t require a temporary variable and makes it clear that the reading and conversion code together produce the value for the variable. The advantage to writing the code across two lines with a temporary variable is that it gives you something to examine if you need to run your program in the debugger.
    🔗
    When we read every line from the file using nextLine(), we never mix reading tokens with reading lines, and we no longer need to consume a newline after reading a record. This simplifies the code and improves its readability.
    🔗
    🔗

    Subsection 4.10.6 Variable Roles and Files

    In Section 4.3 we explored four common variable roles (stepper, most-recent holder, most-wanted holder, and gatherer). All of these roles apply when processing file data in a loop, just as they did when reading data from the console.
    🔗
    In Listing 4.19, each of our record variables (name, latitude, longitude, and aqi) is a most-recent holder. Each one stores a single field from the record that was most recently read from the file. These values are processed (in this case, printed), and on the next pass through the loop, they are overwritten by the fields from the next record.
    🔗
    Listing 4.20 adds variables in stepper, most-wanted holder, and gatherer roles to find the city with the cleanest air quality and calculate the average AQI across all cities in the file:

    However, we’re interested in knowing not just the low reading, but which city has the lowest reading, so we must also have a variable to hold the name from the record with the lowest AQI reading. Whenever our test finds a city with a lower AQI than is stored in bestAqi, we update both bestAqi and bestCity to store the corresponding name from the same record.
    🔗
    This is a very common design pattern whenever you need to find an extreme record in a dataset and preserve its identifying details.
