    Section 3.4 Multi-Way Branching (Series and Nested if Statements)

    Imagine that you are asked to write three programs for a professor who is experimenting with different methods of grading her programming course. Students are given a pre-test at the beginning of the course and a post-test at the end. Based on the pre-test and post-test scores, she wants the following programs:
    🔗
    Program 1 simply assigns a letter grade based on the post-test score, where 0 up to 60 is an F, 60 up to 70 is a D, 70 up to 80 is a C, 80 up to 90 is a B, and 90+ is an A.
    🔗
    Program 2 breaks students into pass (70+) and retake (below 70) categories based on their post-test scores, but students in the retake category are further broken into two intervention categories based on their pre-test score: foundational focus for pre-test scores below 60, and conceptual focus for pre-test scores of 60 and above.
    🔗
    Program 3 assigns a pass/retake category based on the same criteria as program 2, but then it also assigns a high achievement badge if the post-test score is at least 40 points higher than the pre-test score.
    🔗
    Each of these programs must include branching code—code that executes only under certain conditions. For example, programs 2 and 3 both split into two paths based on the post-test score, the pass path for scores 70 and higher, and the retake path for scores below 70. But each of these branching problems have properties that require a different branching structure. Let’s examine each.
    🔗

    Subsection 3.4.1 Series if Statements

    Program 1 has five mutually exclusive conditions. Mutually exclusive conditions can’t simultaneously exist. Each one might exist for a different execution of the program, but once the decision code is reached, only one of the mutually exclusive conditions will be true. For example, if the post-test grade is ninety or above, it can’t simultaneously fall into any of the other categories. We can picture this branching structure as multiple distinct branches.
    🔗
    We have already seen how to solve a problem with two mutually exclusive conditions (that completely cover all possibilities)—an if-else structure. With an if-else structure, either a condition is true or its complement (opposite) is true. We extend that pattern when there are more than two mutually exclusive conditions with an if-else if structure, called a series if. A series if is a single if statement. Listing 3.8 is a solution to program 1 that shows only the code within the main method.
    🔗
    The series if statement is on lines 13-23. It begins with the keyword if followed by a condition, and then the conditionally executed code (in this example, {letterGrade = 'F';}). It is then followed by an else. The else’s conditionally executed code is another if, followed by a condition, followed by conditionally executed code. In a series if statement, you can have as many conditions as you need for the problem you’re solving, all following the pattern if-condition-code-else-if-condition-code… etc.
    🔗
    A series if statement is a single if statement. Once a true condition is reached, its conditional code executes and the rest of the statement is skipped. Control will move to the first line of code following the series if. Listing 3.8 executes sequentially until line 13. On line 13, the condition postTestScore < 60 is tested. If that test is true, then line 14 will execute, the rest of the series if will be skipped, and execution will resume on the first line following the series if, which is the print statement on line 26.
    🔗
    If the test on line 13 is false, then the else code executes on line 15. The else code is another if statement. The test for that if statement, postTestScore < 70, executes. If it’s true, the conditional code on line 16 executes, the rest of the series if is skipped, and control resumes on line 26. If the test on line 15 is false, the else code on line 17 is reached. That is another if statement, so that test executes.
    🔗
    This pattern continues through the entire series if statement. If all of the tests are false, line 21 is reached. Line 21 is a simple else followed by an assignment statement. If the else on line 21 is reached, the assignment statement on line 22 will execute.
    🔗
    In a series if, each condition is tested in order until a condition evaluates to true. Once a condition evaluates to true, its conditional code executes and the series if statement is complete. The rest of the series if is skipped and execution resumes at the first line of code following the series if.
    🔗
    Notice the sifting property at work in Listing 3.8. The first condition (postTestScore < 60) catches every score below 60. If execution falls through to the next condition (postTestScore < 70), we already know the complement must be true: postTestScore >= 60. As a result, when postTestScore < 70 evaluates to true, the score is guaranteed to be in the range \([60.0, 70.0)\text{.}\) Each successive branch sifts out the next layer of values.
    🔗
    Listing 3.8 is a series if with a final else that has no condition. This means one branch of the series if will always execute—if none of the conditions evaluate to true, then the final else will execute. This is not required. How you structure a series if depends on the problem you’re solving. It may be that you want code to execute for some number of mutually exclusive conditions, but there are some cases that require no response. In that case, you may write a series if that has no “default” else at the end.
    🔗
    Be careful, though, if you’re assigning a value to a variable in a series if. If the series if doesn’t cover all possible cases, then you may end up with a variable without a value, which could cause a compiler error later when you include the variable in a computation or try to print its value. To solve that, don’t just assign a default value to the variable—make sure you’re giving it the correct value for all possible conditions.

    Subsection 3.4.2 Nested if Statements

    Program 2 begins with two mutually exclusive conditions, assigning a grade of either pass or retake based on the post-test score. We know that we can use an if-else statement to solve this problem. However, if a grade is assigned to the retake category, we must then examine the pre-test score and further assign either a foundational focus or a conceptual focus.
    🔗
    Problem 2 involves a nested condition—we need to test the pre-test score only after we’ve tested the post-test score and selected the retake branch. We can picture this branching structure as a tree with some number of branches (in this example, two). One (or more) of the branches then also branches. (In our example, only one of the branches itself has branches.)
    🔗
    Listing 3.10 shows the branching code after the variables preTestScore and postTestScore have been read from the keyboard.
    🔗
    The structure of a nested solution is to include a complete if statement within the conditional code of either an if or else branch. The nested if statement can be any of the if statements we’ve learned, such as a simple if, an if-else, or a series if. In Listing 3.10, we see an if-else nested within the else branch of an if-else. We refer to the first if as the outer if statement, and the if statement nested within the else as an inner if statement. (It might be helpful to picture Russian nesting dolls when considering the terms “inner” and “outer” in an if statement.) We are not restricted to a single level of nesting—it depends on the problem being solved.
    🔗
    In an if statement, once the condition has been evaluated, one of the conditional blocks is selected to execute. (For example, in an if-else, the if block is selected if the condition is true, and the else block is selected if the condition is false.) Within the block, execution begins sequentially, with the first line of code in the block. In Listing 3.10, if we enter the else branch on line 4, the first line of code to execute is the assignment statement on line 5. Java then executes line 6, which is an if statement. If the test on line 6 is true, line 7 will execute. If it’s false, the else block on line 9 will execute. Execution then proceeds sequentially after the if-else statement within the outer else block. Because there is no more code within the outer else block, execution proceeds sequentially after the outer if.
    🔗
    In Listing 3.10, if the outer if condition on line 2 evaluates to true, line 3 will execute and then execution will proceed to the first line of code after line 11. The else block and its nested if will never be reached.
    🔗
    It can sometimes be tricky to read a nested if, especially if the programmer has not put curly braces around the blocks. (This is one reason most style guides recommend you always put curly braces around conditionally executed code.) For example, consider this code:
    🔗
    if (postTestScore < 70) 
    if (preTestScore < 60) 
        result = "Retake with foundational intervention.";
else
    result = "Pass.";
    Which if does the else pair with? Remember that Java ignores indentation. The indentation tells us that the programmer intended for the else to pair with the outer if, but when there are no curly braces, Java follows the rule that an else always pairs with the nearest if that doesn’t already have an else. Therefore, the else pairs with the inner if (preTestScore < 60). In this example, the indentation communicates the wrong pairing. (You can paste this code into Eclipse, select it, and choose Source → Correct Indentation. Eclipse will show us that the else is paired with the inner if.)
    🔗
    If the programmer wanted the else to pair with the outer if, they could include curly braces around the conditional code for the outer if. The closing curly brace ends the outer if block’s conditional code:
    🔗
    if (postTestScore < 70) { 
    if (preTestScore < 60) 
        result = "Retake with foundational intervention.";
} else
    result = "Pass.";
    It is very common for there to be multiple closing curly braces at the end of a block of code. Even when they’re properly indented, it can be difficult to see which opening curly brace is a match. Some Java style guides recommend documenting closing curly braces with single-line comments. If our code from Listing 3.10 were the end of the program, the program would end with four closing curly braces, which we might document as shown below, to make the code more readable and easier to modify. If you wanted to add a print statement to display the result, you’d know to put it between the second and third curly braces so that it would fall within the main method, but after the conditional code that sets the result variable.
    🔗
            } // end if preTestScore < 60
    } // end if postTestScore >= 70
} // end main
} // end GradingProgram2

    Subsection 3.4.3 Separate if Statements

    Our third grading scenario presents a different challenge: Program 3 assigns a pass/retake status based on the post-test score, but it also awards a high achievement badge if the post-test score is at least 40 points higher than the pre-test score.
    🔗
    Notice how this differs fundamentally from Programs 1 and 2:
    🔗
    • In Program 1, the outcomes are mutually exclusive—a student cannot be assigned both a 'B' and a 'C'.
      🔗
      🔗
    • In Program 2, the intervention category is hierarchically dependent—we only evaluate the pre-test score if the student needs a retake.
      🔗
      🔗
    • In Program 3, the two decisions are independent. A student who passes might earn the badge, but a student who needs a retake could also earn the badge (for instance, improving from a pre-test score of 15 to a post-test score of 55 shows a 40-point leap, even though 55 requires a retake).
      🔗
      🔗
    Because these conditions are not mutually exclusive and neither is subordinate to the other, we must use separate, standalone if statements. Listing 3.11 shows the decision code for Program 3.
    🔗
    In a series if-else-if, choosing one branch bypasses the rest. In nested if statements, inner branches are locked behind an outer gate.
    🔗
    With separate if statements, every condition is evaluated. The program evaluates postTestScore >= 70. Regardless of whether the if or else branch executes, control moves sequentially to the next statement. The program then evaluates postTestScore - preTestScore >= 40. It does not matter what happened in the first decision; this second check always occurs.
    🔗
    A very common beginner mistake is confusing separate if statements with a series if-else-if. Consider what would happen if we tried to write Program 1 using separate if statements instead of a series:
    🔗
    // BUG: Multiple separate ifs instead of a series
if (postTestScore < 60) {
    letterGrade = 'F';
}
if (postTestScore < 70) {
    letterGrade = 'D'; // Overwrites 'F'!
}
if (postTestScore < 80) {
    letterGrade = 'C'; // Overwrites 'D'!
}
    If a student scores a 50, the first if sets letterGrade to 'F'. But because the next statement is an independent if, Java evaluates 50 < 70 (true) and overwrites the grade with 'D'. It then evaluates 50 < 80 (true) and overwrites it with 'C'.
    🔗
    Use a series if-else-if when you want at most one branch to execute. Use separate if statements when multiple independent actions may all need to execute during the same program run.

    What value is stored in grade after the following code executes?
    🔗
    int score = 55;
char grade;
if (score < 60) {
    grade = 'F';
}
if (score < 70) {
    grade = 'D';
}
if (score < 80) {
    grade = 'C';
}
    • 'C'
    • Correct! Because these are separate if statements rather than else if, all three conditions are evaluated and each true condition overwrites grade, leaving 'C'.
    • 'F'
    • Not quite. grade would stay 'F' only if the second and third checks used else if. Here, all three separate if statements run.
    • 'D'
    • Not quite. After 55 < 70 sets grade to 'D', Java still evaluates 55 < 80, which overwrites grade with 'C'.
    • It causes a compiler error because grade is assigned more than once.
    • Not quite. Variables can be reassigned as many times as needed; the issue here is a logic bug from using separate if statements instead of a series if-else-if.

    3. Tracing an Unbraced Nested if.

    What is stored in msg after the following code executes?
    🔗
    int a = 10;
int b = 2;
String msg = "Start";
if (a < 5)
    if (b < 5)
        msg = "Both";
else
    msg = "Outer else";
    • "Start"
    • Correct! Because there are no curly braces, the else pairs with the nearest if (if (b < 5)). Since 10 < 5 is false, the entire inner if-else is skipped and msg remains "Start".
    • "Outer else"
    • Not quite. Java ignores indentation; without curly braces, else always pairs with the nearest preceding if (if (b < 5)), not the outer if.
    • "Both"
    • Not quite. Since a is 10, a < 5 is false, so the inner if (b < 5) never executes.
    • It causes a compiler error because the else is indented to match the outer if.
    • Not quite. Java ignores whitespace and indentation; the code compiles, but behaves differently from what the indentation suggests.
