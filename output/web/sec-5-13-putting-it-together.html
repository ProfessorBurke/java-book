    Section 5.13 Putting It All Together: A Complete Case Study

    You now have all the tools you need to solve problems by decomposing them into sub-tasks implemented with methods. Let’s work through an example problem and then you can try some of the exercises at the end of the chapter.
    🔗
    Two six-sided dice. © Schlurcher, retrieved from Wikimedia Commons.
    🔗

    Subsection 5.13.1 The Problem

    Design a game for one user to play against the computer. The game will simulate the roll of a six-sided die. In the game, the players are trying to reach a threshold value by totaling die rolls. The game is over when one player reaches the threshold value (wins) or goes over the threshold (loses).
    🔗
    The players take turns rolling the die. The value of the die is added to their total. The game is over when one of the following occurs:
    🔗
    • One player’s total equals the threshold (a win).
      🔗
      🔗
    • One player’s total exceeds the threshold (a loss, called a bust).
      🔗
      🔗
    The game will proceed in rounds. Each round, the die will be rolled for the user and added to their total. The program will report the die roll. The program will print a message if the user has won or busted. If they haven’t, the die will be rolled for the computer and the roll will be reported. The program will print a message if the computer has won or busted. Both total scores will be reported, and if nobody has won or busted, the program proceeds to the next round.
    🔗
    Note that you can enhance this game by giving both players the chance to hold—to stop rolling. This adds one more ending condition to the game: both players have chosen to hold. We will implement the simpler version of the game.
    🔗
    🔗

    Subsection 5.13.2 Decomposing the Problem

    To begin, we look for subtasks within the problem. While there are many ways to break a problem apart, we evaluate our proposed decomposition using the following criteria:
    🔗
    • Single Responsibility: Each subtask focuses on one specific job that can be described in a simple sentence.
      🔗
      🔗
    • Reusability: The subtask eliminates duplicated code by packaging operations that occur multiple times (such as taking a turn for either the player or the computer).
      🔗
      🔗
    • Information Hiding: The subtask hides low-level details or complex formulas so the higher-level program remains easy to read.
      🔗
      🔗
    • Well-Defined Contract: We can clearly define the subtask’s interface: its inputs (parameters), its output (return value), and its pre- and postconditions.
      🔗
      🔗
    • No Reinventing the Wheel: The task is not already handled directly by an existing Java library method (such as System.out.println or Math.max).
      🔗
      🔗
    Using these criteria, we will break the problem down into a main method and helper methods. Figure 5.16 is a structure chart depicting the program structure, including the data that will flow between these methods.
    🔗
    From the structure chart, you can see that main calls rollDie, isGameOver, and displayOutcome. The algorithm within main (including where the methods are called) is:
    🔗
    Print a welcome message
While the game isn't over:
    Take the user's turn (rollDie)
    If the user didn't win or bust (isGameOver)
        Take the computer's turn (rollDie)
        Check if the computer won or busted (isGameOver)
    Print the scores 
Announce the winner or loser (displayOutcome)
    Let’s look at some of the design decisions made here and how they meet our evaluation criteria.
    🔗

    Subsubsection 5.13.2.1 Separating Announcing a Win or Loss from Determining if the Game is Over

    The isGameOver method is given a score and the threshold, and it determines if there’s a win or a bust. It could also print messages for these two states, either generically (e.g. “That’s a bust!”), or if another parameter is passed identifying the player, it could provide a message like displayOutcome (“That’s a win for you!” or “That’s a win for the computer!”). However, if we designed isGameOver to perform these two tasks, then we would be violating our Single Responsibility principle.
    🔗
    Separating the functionality into two separate methods gives each method a clear and simple contract with the rest of the program, making the method easier to write and test. It also makes the program easier to expand and modify. If we planned to enhance the game to allow the user or computer to hold at a particular total, we would need to modify isGameOver to consider this third condition (both players holding), and we would need to modify displayOutcome to look for a new win condition—both scores at or below the threshold and one score higher than the other. There is also now the potential for a tie. It will be much easier to make these modifications without the complexity of having to make both sets of changes in one method.
    🔗
    🔗

    Subsubsection 5.13.2.2 Writing a General rollDie Method Rather than Two Separate Methods

    In the game, both the user and the computer roll the die, so it might be tempting to design two separate rollDie methods—one for the user and one for the computer. But if you were to implement both methods, you’d quickly discover that the methods are identical. Therefore only one method is needed, and can be called twice.
    🔗
    Sometimes there is code or functionality that is not quite identical. In those cases, you can factor the code into a single method. Any differences between the methods are added as parameters to specialize the method functionality.
    🔗
    🔗

    Subsubsection 5.13.2.3 Hiding Low-Level Details

    It might be tempting in main to generate the die roll directly inside it using a single line of arithmetic:
    🔗
    int roll = (int)(Math.random() * numSides) + 1;
    Why did we bother extracting this single line of code into its own helper method, rollDie?
    🔗
    We did so to practice information hiding. Even though the code is short, scaling a pseudo-random floating-point number into an integer range requires non-trivial mechanics: multiplying by numSides, applying operator precedence, casting to an integer, and shifting the result by one. Placing that expression inside main forces anyone reading the turn logic to mentally unpack that mathematical formula.
    🔗
    Extracting that calculation into rollDie(numSides) offers three major software engineering benefits:
    🔗
    • Intent-Revealing Code: The method call rollDie(numSides) immediately communicates what is happening in plain English, allowing main to stay focused on high-level turn progression rather than math mechanics.
      🔗
      🔗
    • Isolated Verification: We can equip rollDie with its own precondition assertion (assert numSides > 0) and postcondition assertion (assert 1 <= dieRoll && dieRoll <= numSides) to guarantee that the random number generation is strictly bounded before the rest of the game uses it.
      🔗
      🔗
    • Flexibility for Future Change: If we later decide to simulate rolling physical dice using a seeded java.util.Random generator or an external hardware sensor, we only have to modify the body of rollDie. The calling method, main, remains completely unchanged.
      🔗
      🔗
    🔗

    Subsubsection 5.13.2.4 Knowing When Not to Decompose: Avoiding Unnecessary Wrappers

    Our final evaluation criterion is ensuring that we do not reinvent the wheel. Just as important as knowing when to create a method is knowing when to leave code in main.
    🔗
    In our game, we need to print a two-line welcome banner at the start, and we need to display the current scores at the end of each round:
    🔗
    System.out.println("Your score          ---> " + playerTotal + ".");
System.out.println("The computer's score ---> " + computerTotal + ".
");
    We could have created a printGreeting() method and a showScores() method. However, doing so would add visual clutter without providing any real abstraction. Neither task involves calculations, neither hides complex decisions, and neither requires parameterized customization.
    🔗
    Standard output statements using System.out.println are already simple, standard library tools. Wrapping a couple of straightforward print statements inside a custom helper method creates an unnecessary layer of indirection—it forces someone reading your program to jump down to a helper method body just to see a basic print call.
    🔗
    Good software design is about balance: decompose code when it eliminates duplication, separates distinct responsibilities, or clarifies complex algorithms, but leave straightforward sequential statements right where they occur.
    🔗
    🔗
    🔗

    Subsection 5.13.3 Write Method Contracts and the Testing Plan

    Before implementing the solution, we precisely specify each method’s contract: its inputs, outputs, preconditions, and postconditions. This facilitates building each method as a component that can be smoothly integrated into the final system. We should also design a testing plan for each method so we can unit test our methods before we integrate.
    🔗

    Subsubsection 5.13.3.1 Writing a Method Contract

    The contracts for each method in our program are documented in the Javadoc comment above each method in the solution (Listing 5.19), but we’ll discuss one method in detail: rollDie.
    🔗
    From the structure chart, you can see that rollDie takes one input: the number of sides of the die being rolled (an int). It randomly generates and returns a roll between one and the number of sides (inclusive).
    🔗
    What is the contract between rollDie and its calling method? As a precondition, we specify numSides >= 1. How did we determine that? First, from a domain perspective, a die represents a physical object—a die with zero or negative sides does not exist in reality. (We might argue that a die with one side, which would always roll a one, also doesn’t exist! We decided to allow it because the method can return a meaningful result with that input.) From an algorithmic perspective, our scaling formula (int)(Math.random() * numSides) + 1 mathematically assumes a positive scaling factor. Passing a negative number breaks the uniform distribution due to integer truncation.
    🔗
    The precondition numSides >= 1 protects both the integrity of our game’s rules and the mathematics of our random generation.
    🔗
    Given that precondition, our postcondition is that the value returned will be between \(1\) and numSides inclusive.
    🔗
    To check the precondition, we write an assert statement before we generate the random roll value:
    🔗
    assert numSides > 0 : "rollDie called with d" + numSides;
    We can also check the postcondition at the end of the method:
    🔗
    assert 1 <= dieRoll && dieRoll <= numSides : "Randomly generated value out of range";
    This ensures that our algorithm is never generating a value outside of the expected range, which would indicate a problem with the method’s code.
    🔗
    🔗

    Subsubsection 5.13.3.2 Writing a Method’s Testing Plan

    To test rollDie, we divide the input domain into two equivalence classes: an invalid partition (numSides <= 0) where the method’s precondition assertion should trip, and a valid partition (numSides >= 1) where the method should return a random integer between \(1\) and numSides. To trip the assertion, we can use the boundary value of 0.
    🔗
    For valid inputs, however, we cannot predict the exact value returned by any single call because the result is pseudo-random. So how do we test a method that generates a random number? We want to ensure two things:
    🔗
    1. The method never generates a value outside of the postcondition range.
      🔗
      🔗
    2. The method will generate all of the numbers within the range.
      🔗
      🔗
    To ensure that both conditions are met, we can write a test method that invokes rollDie in a loop with flags for each value in the expected range (e.g. 1–6 for a numSides value of 6) and a check that no value is out of the range. If each value is seen at least once and no value is ever generated outside of the range, we know our postcondition is met. The loop must iterate enough times to ensure that each number has a high probability of being generated. For a range of 1–6, a loop that iterates 1,000 times is an excellent choice because the loop will run in less than a millisecond, and because there is a less than one-in-a-trillion chance that one of the six numbers won’t be generated if the code is correct. For a much larger numSides value, such as 100, you should run the loop about 2,000

    Subsection 5.13.4 Implementing the Solution

    Once each method’s contract and test plan are established, the methods can be individually implemented and unit-tested. In parallel, the DiceGame class and its main method can be written, using stubs in place of the helper methods until each one is ready for integration. On a professional software engineering team, different engineers might implement different helper methods simultaneously; shared method contracts ensure that all the components fit together seamlessly during integration.
    🔗
    A method stub consists of a complete method header followed by a minimal body: an empty block for a void method, or a single statement returning a dummy value for a value-returning method. For example, a stub for rollDie can be written as:
    🔗
    public static int rollDie(int numSides) {
    return 1; // Temporary dummy return value
}
    Stubs allow main to compile and execute immediately. In fact, if you pair this rollDie stub with a basic isGameOver stub and an empty displayOutcome stub, you can run a complete, deterministic simulation of the game: both players will roll 1 on every turn, and the game loop will reliably terminate after exactly 15 rounds. This allows you to verify the overall control flow in main before writing a single line of random number generation.
